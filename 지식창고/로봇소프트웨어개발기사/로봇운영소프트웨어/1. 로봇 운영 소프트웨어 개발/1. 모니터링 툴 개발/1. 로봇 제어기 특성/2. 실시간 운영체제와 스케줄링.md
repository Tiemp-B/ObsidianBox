# Summary

[[RTOS]](Real-Time Operating System)는 정해진 시간(데드라인) 안에 작업을 반드시 완료하는 것을 목표로 설계된 운영체제다. 일반 OS가 "평균적으로 빠른 처리(높은 처리량)"를 지향한다면, RTOS는 "최악의 경우에도 데드라인을 지키는 것(결정적 응답시간)"을 지향한다는 점이 근본적인 차이다. 로봇 제어기의 OS 계층은 서보 루프(수백 μs~수 ms 주기)가 매 주기마다 정확히 실행되도록 태스크 스케줄링과 인터럽트 우선순위를 관리하며, 이 노트는 RTOS의 정의, 스케줄링 알고리즘([[Rate Monotonic Scheduling]] 등), 인터럽트 우선순위 처리, 실시간 제약조건을 다룬다.

# Notes

<aside>RTOS란 무엇인가</aside>

RTOS는 태스크가 **정해진 시간 제약(데드라인)** 안에 실행을 마치는 것을 보장하도록 설계된 운영체제다.

- **실시간 처리(Real-time Processing)의 정의**: 처리 속도가 절대적으로 빠른 것이 아니라, **정해진 시간 내에 작업을 완료**하는 것이 핵심이다. 아무리 평균 응답이 빨라도 한 번이라도 데드라인을 놓치면 실시간 시스템으로서는 실패로 간주된다.
- 로봇 제어에서는 센서 읽기 → 제어 연산 → 액추에이터 출력까지의 서보 루프가 정확한 주기로 반복되어야 안전하고 정밀한 동작이 가능하다.

**실시간 시스템의 3가지 분류**

| 구분 | 데드라인을 놓쳤을 때 | 예시 |
|---|---|---|
| Hard Real-Time | 시스템 전체가 실패(치명적) | 로봇 서보 제어 루프, 자동차 에어백 |
| Firm Real-Time | 결과는 무의미해지지만 치명적이진 않음 | 일부 센서 샘플링 |
| Soft Real-Time | 성능이 저하될 뿐 계속 동작 | 모니터링 화면 갱신, 로깅 |

로봇 제어기의 저수준 제어 계층(서보 루프)은 **Hard Real-Time**, 응용/모니터링 계층은 대체로 **Soft Real-Time**으로 분류된다.

<aside>일반 OS와의 차이</aside>

| 항목 | 일반 OS (Windows, 일반 Linux) | RTOS |
|---|---|---|
| 목표 | 높은 평균 처리량(Throughput) | 결정적 응답시간(Deterministic Response) |
| 스케줄링 기준 | 공정성(Fairness), 처리량 | 데드라인 준수, 우선순위 |
| 인터럽트 지연 | 가변적 | 최소화·예측 가능 |
| 사용자 인터페이스 | 화려한 GUI 지원이 목적에 부합 | GUI는 부차적 — 화려함이 목적이 아님 |

> **⚠ 자주 나오는 오답 함정**: "RTOS는 높은 처리량이 특징이다", "RTOS는 화려한 사용자 인터페이스를 제공한다"는 모두 **틀린 설명**이다. RTOS의 본질은 처리량이나 UI가 아니라 **결정적 응답시간**이다.

<aside>스케줄링 알고리즘</aside>

RTOS의 태스크 스케줄링은 대부분 **우선순위 기반 선점형(Preemptive Priority-based) 스케줄링**을 사용한다.

- **Rate Monotonic Scheduling (RMS)**: 고정 우선순위 스케줄링의 대표 알고리즘. **주기(Period)가 짧은 태스크일수록 높은 우선순위**를 부여한다. 실행 시간이나 데드라인의 길이가 아니라 **주기의 길이**가 우선순위 결정 기준이다.
    - 자세한 개념은 [[Rate Monotonic Scheduling]] 참고
- **[[Earliest Deadline First(EDF)|Earliest Deadline First (EDF)]]**: 동적 우선순위 방식으로, 그 순간 **데드라인이 가장 임박한 태스크**에 가장 높은 우선순위를 부여한다. 이론적으로 RMS보다 CPU 활용률이 높지만 구현이 복잡하다.
- **라운드 로빈(Round Robin)**: 일반 OS의 시분할 스케줄링 방식으로, 태스크에 균등한 시간 조각(Time Slice)을 순환 배분한다. **RTOS의 실시간 스케줄링 방식이 아니며**, 인터럽트 우선순위 결정 방식도 아니다.

<aside>인터럽트 처리와 우선순위</aside>

인터럽트는 하드웨어 이벤트(센서 데이터 도착, 타이머 만료 등) 발생 시 CPU가 현재 작업을 중단하고 즉시 처리하는 메커니즘이다. 인터럽트 서비스 루틴([[인터럽트 서비스 루틴(ISR)|ISR]])이 실행을 담당한다.

**인터럽트 우선순위 결정 방식**
- **고정 우선순위 방식**: 인터럽트 소스별로 미리 정해진 우선순위 사용
- **동적 우선순위 방식**: 상황에 따라 우선순위가 실시간으로 변경
- **중첩 인터럽트(Nested Interrupt) 방식**: 처리 중인 인터럽트보다 더 높은 우선순위의 인터럽트가 발생하면 이를 선점하여 먼저 처리
- ~~라운드 로빈 방식~~ → 이는 프로세스/태스크 스케줄링 기법이며, **인터럽트 우선순위를 결정하는 방식이 아니다** (자주 출제되는 오답 선택지)

인터럽트는 처리의 **긴급성(Urgency)**에 따라 우선순위가 결정되는 것이 원칙이다.

<aside>우선순위 역전과 상속</aside>

여러 우선순위의 태스크가 공유 자원을 두고 경쟁할 때 **우선순위 역전([[우선순위 역전(Priority Inversion)|Priority Inversion]])** 현상이 발생할 수 있다. 낮은 우선순위 태스크가 공유 자원(뮤텍스 등)을 점유한 상태에서 높은 우선순위 태스크가 그 자원을 기다리게 되면, 결과적으로 높은 우선순위 태스크가 낮은 우선순위 태스크에 의해 지연되는 역설적 상황이 생긴다.

- **해결책 — 우선순위 상속 프로토콜(Priority Inheritance Protocol)**: 낮은 우선순위 태스크가 공유 자원을 사용 중일 때, 그 자원을 기다리는 높은 우선순위 태스크의 우선순위를 낮은 우선순위 태스크에게 **일시적으로 상속**시켜 우선순위 역전을 방지한다.
- 동기화 메커니즘(뮤텍스/세마포어) 자체에 대한 내용은 [[3. 동기화 메커니즘(세마포어·뮤텍스·데드락)]] 참고

<aside>실시간 제약조건 정리</aside>

실시간 시스템을 설계·평가할 때 고려하는 핵심 제약조건:

- **데드라인(Deadline)**: 태스크가 반드시 완료되어야 하는 시점
- **주기성(Periodicity)**: 태스크가 반복 실행되는 주기
- **우선순위(Priority)**: 태스크 간 실행 순서를 결정하는 기준
- **지터(Jitter)**: 태스크 실행 시작/종료 시점의 변동폭 — 작을수록 예측 가능성이 높음
- **[[WCET(Worst Case Execution Time)|WCET]] (최악 실행 시간)**: 태스크가 실행되는 데 걸리는 시간의 이론적 최댓값. 스케줄링 가능성 분석의 기초 데이터

> **⚠ 오답 함정**: "코드 복잡도"는 소프트웨어 품질 지표(유지보수성과 관련)이지, 실시간 제약조건이 아니다.

<aside>대표 RTOS와 로봇 적용 사례</aside>

- **[[VxWorks]], [[QNX]]**: 항공우주·산업용 로봇 컨트롤러에서 널리 사용되는 상용 RTOS
- **[[RT-Linux]] / [[Xenomai]] / [[PREEMPT_RT]]**: 일반 Linux 커널에 실시간 확장을 적용한 오픈소스 계열. ROS/ROS2와 함께 사용되는 경우가 많음
- **[[FreeRTOS]]**: 임베디드 MCU(모터 드라이버 펌웨어 등)에서 널리 쓰이는 경량 RTOS

로봇 제어기에서는 저수준 제어 계층(서보 루프)만 RTOS 위에서 Hard Real-Time으로 동작시키고, 모니터링·로깅 등 응용 계층은 일반 OS(Soft Real-Time)에서 처리하는 **하이브리드 구조**가 일반적이다.

<aside>핵심 정리</aside>

- RTOS의 본질은 **결정적 응답시간**이지, 높은 처리량이나 화려한 UI가 아니다
- 실시간 처리 = **데드라인 준수**, 단순히 빠른 처리와는 다른 개념
- RMS는 **주기가 짧을수록 높은 우선순위**를 부여하는 고정 우선순위 스케줄링
- 인터럽트 우선순위는 고정/동적/중첩 방식으로 결정되며, **라운드 로빈은 해당하지 않음**
- 실시간 제약조건은 데드라인·주기성·우선순위(·지터·WCET)이며, **코드 복잡도는 해당하지 않음**
- 우선순위 역전은 **우선순위 상속 프로토콜**로 해결
