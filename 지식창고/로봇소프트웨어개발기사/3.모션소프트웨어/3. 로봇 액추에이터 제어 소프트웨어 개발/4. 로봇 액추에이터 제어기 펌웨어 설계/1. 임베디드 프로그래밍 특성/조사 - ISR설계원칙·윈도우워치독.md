# 조사 - ISR설계원칙·윈도우워치독 (2026-08-09)

개요(허브) 링크 정상, NCS 자료 대조 aside 없음(이미 클린). 문제은행(세부항목 슬롯 10문항 중 이 세세항목 소관 "문맥교환 설명 틀린것"·"워치독 목적"·"워치독 설명 틀린것"·"인터럽트 처리방식 틀린것" 4문항) 전부 기존 페이지 커버 확인, PWM 주파수·뮤텍스/세마포어·상태머신·동기화·멀티스레딩 관련 6문항은 형제 세세항목("2. 로봇 액추에이터 펌웨어 구조", "3. 로봇 액추에이터 펌웨어 설계") 소관으로 확인. 3라운드 웹검색 반복 적용.

## Phase 1 — 3라운드 반복 검색

### 1라운드 — 후보 개념 탐색
- "interrupt service routine ISR design principle keep short embedded real-time system" 검색 → ISR은 최대한 짧게 작성해야 하며(실행 중 다른 인터럽트가 지연·유실될 수 있음), 무거운 처리는 최소한의 확인 작업만 ISR에서 하고 나머지는 이후(태스크·메인루프)로 미뤄야 한다는 원칙 확인 — 기존 페이지는 "우선순위가 높은 인터럽트를 먼저 처리"라고만 하고, ISR 자체를 어떻게 작성해야 하는지 원칙이 없음(신규 공백)
- "window watchdog timer vs standard watchdog too early too late kick difference" 검색 → 일반 워치독은 리셋 신호가 "너무 늦게" 오는 경우만 감지하지만, **윈도우 워치독**은 "너무 이르게" 오는 경우(빠른 루프에 갇힌 경우 등)까지 함께 감지한다는 차이 확인 — 기존 페이지는 일반 워치독의 kick/timeout만 다루고 이 구분이 없음(신규 공백)

### 2라운드 — 파생 심화 검색
- "ISR 인터럽트 서비스 루틴 짧게 작성 이유 임베디드 실시간" 검색 → 인터럽트 처리 중에는 다른 인터럽트가 비활성화되는 경우가 많아 ISR이 길면 다른 인터럽트를 놓치거나 지터·지연이 발생한다는 이유 확인, 무거운 작업은 나중으로 미루는 접근(2단계 처리) 확인
- "윈도우 워치독 타이머 일반 워치독 차이 너무 빠른 리셋 감지" 검색 → 한국어 자료로 윈도우 워치독이 카운터 값이 지정된 임계값 미만일 때(너무 빠른 리셋 시도) 시스템 리셋을 트리거한다는 구체적 동작 확인

### 3라운드 — 반영 후보 구체화 검증
- "인터럽트 서비스 루틴 무거운 작업 태스크로 미루기 bottom half deferred" 검색 → 리눅스 커널의 "bottom half"처럼 인터럽트 처리를 최소 확인 작업(ISR)과 나머지 처리(태스크)로 나누는 개념을 확인했으나, 이는 OS 커널 수준의 세부 용어라 §2 원칙상 이 노트에는 "최소한의 작업만 하고 무거운 처리는 나중으로 미룬다"는 원칙 수준까지만 반영하기로 확정(bottom half라는 용어 자체는 넣지 않음)

## Phase 2 — 자체 검토

- ISR 설계 원칙은 기존 "인터럽트 처리 흐름" aside를 완성하는 자연스러운 확장이며, "짧게 작성해야 하는 이유"(다른 인터럽트 유실·지연 방지)까지만 반영하고 구체적 클럭 사이클 수치나 OS별 후반부 처리 기법(태스크릿·워크큐 등)까지는 넣지 않음(§2 원칙)
- 윈도우 워치독은 기존 워치독 타이머 aside의 "너무 늦은 리셋만 감지"라는 암묵적 전제를 넘어서는 대안 방식이라 반영하되, 구체적 레지스터 설정값이나 제조사별 구현 차이까지는 넣지 않음
- 두 개념 모두 기존 aside를 구체화·확장하는 수준이라 별도 Box 용어보다는 기존 페이지 보강으로 처리

## Phase 3 — 결론

2개 페이지(2. 인터럽트와 문맥교환, 3. 워치독 타이머)에 신규 개념 2건(ISR을 짧게 작성해야 하는 원칙, 윈도우 워치독) 반영. 신규 Box 용어 없음, 기존 `워치독 타이머(Watchdog Timer)` 용어에 보강.
