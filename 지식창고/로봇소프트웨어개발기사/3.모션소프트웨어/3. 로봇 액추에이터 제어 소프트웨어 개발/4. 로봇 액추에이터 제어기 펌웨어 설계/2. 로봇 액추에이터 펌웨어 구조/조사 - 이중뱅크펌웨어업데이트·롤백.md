# 조사 - 이중뱅크펌웨어업데이트·롤백 (2026-08-09)

개요 페이지에 "NCS 자료 대조" aside가 있어 이번 재작업에서 직접 재편집하며 삭제(2026-08-09 규칙). 이 세세항목 소관 문제은행 문항은 없음(펌웨어/부트로더를 직접 묻는 문항이 슬롯에 없음, 나머지 문항은 형제 세세항목 소관). 3라운드 웹검색 반복 적용.

## Phase 1 — 3라운드 반복 검색

### 1라운드 — 후보 개념 탐색
- "dual bank firmware update bootloader fail-safe A/B partition embedded MCU" 검색 → 이중 뱅크(dual-bank) 부트로더는 현재 실행 중인 뱅크(A)는 그대로 구동하면서 새 펌웨어를 비활성 뱅크(B)에 받아 검증한 뒤 전환하는 구조로, 업데이트가 실패해도 기존 뱅크로 되돌아갈 수 있어 기기가 "벽돌"이 되는 것을 막는다는 점 확인 — 기존 페이지는 부트로더의 기본 역할(하드웨어 초기화, 커널 적재)만 있고, 업데이트 실패 시 안전장치가 전혀 없음(신규 공백)
- "bootloader application firmware update process verify rollback failure power loss" 검색 → 새 펌웨어는 첫 부팅 시 자체 검증을 통과해야 확정(confirm)되며, 검증 실패·전원 차단 등으로 중단되면 부트로더가 이전의 정상 펌웨어로 자동 롤백한다는 절차 확인

### 2라운드 — 파생 심화 검색
- "이중 뱅크 부트로더 펌웨어 업데이트 실패 롤백 안전 구조" 검색 → 한국어 자료로 A 뱅크(현재 실행 중)는 계속 구동하며 B 뱅크에 새 버전을 받는 이중 뱅크 구조와, 자동차·임베디드 시스템에서 널리 쓰인다는 점 재확인
- "임베디드 펌웨어 업데이트 정전 전원차단 안전 롤백 구조 A B 파티션" 검색 → 새 펌웨어 부팅 실패 시 다음 부팅을 기존 A 슬롯으로 되돌리는 롤백 기능, 정전 등으로 업데이트가 완전히 기록되지 못했을 때를 대비한 안전장치가 있다는 점을 한국어 자료로 재확인 — "벽돌(브릭)이 되는 것을 막는다"는 실무적 비유 확인

### 3라운드 — 반영 후보 구체화 검증
- 1·2라운드 결과 재검토 → 이중 뱅크 구조(현재 뱅크 구동 유지 + 비활성 뱅크에 새 펌웨어 다운로드·검증) → 검증 통과 시에만 전환, 실패·중단 시 기존 뱅크로 롤백이라는 핵심 흐름을 최종 확정. 로봇 액추에이터 제어기처럼 현장에 배치된 무인 장비에서 펌웨어 업데이트 도중 실패해 완전히 먹통이 되는 것을 막는 실무적 중요성과 직결됨을 확인

## Phase 2 — 자체 검토

- 이중 뱅크·롤백은 기존 페이지가 다룬 부트로더의 "기본 역할"을 넘어, 실무에서 부트로더가 왜 중요한지(안전한 업데이트)를 보여주는 자연스러운 확장이라 반영
- 구체적 플래시 메모리 주소 배치나 서명 검증(디지털 서명) 알고리즘까지는 심화·보안 범위라 넣지 않고, "두 개의 뱅크로 나눠 실패해도 기존 것으로 되돌아간다"는 핵심 구조까지만 반영(§2 원칙)
- 범용적으로 재참조될 수 있는 개념이라 Box 용어로 생성

## Phase 3 — 결론

1개 페이지(2. 펌웨어의 개념과 부트로더)에 신규 개념 1건(이중 뱅크 펌웨어 업데이트와 롤백) 반영. 개요 페이지의 NCS 자료 대조 aside 삭제. 신규 Box 용어 `이중 뱅크(A/B) 펌웨어 업데이트` 생성.
