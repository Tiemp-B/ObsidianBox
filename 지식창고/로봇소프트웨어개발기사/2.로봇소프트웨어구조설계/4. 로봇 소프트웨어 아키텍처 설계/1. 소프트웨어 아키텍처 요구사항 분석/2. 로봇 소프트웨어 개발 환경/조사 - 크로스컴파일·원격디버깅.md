# 조사 - 크로스컴파일·원격디버깅 (2026-08-07)

개요(허브) 링크 정상. 문제은행 2문항(Docker/IDE) 전부 기존 페이지 커버 확인.

## Phase 1 — 조사

### 크로스 컴파일(Cross-Compilation)과 원격 디버깅 — 로봇 개발 환경의 특수성 (신규)
- 기존 페이지2는 IDE 기능을 "코드 편집·빌드·디버깅·버전 관리"로 일반적으로만 서술하는데, **로봇처럼 개발 PC와 실제 실행 장치(타겟)의 프로세서 구조가 다른 임베디드 환경**에서는 이 빌드·디버깅 과정이 일반 PC 개발과 다르게 이뤄진다는 점이 빠져 있었음
- **크로스 컴파일**: 개발 PC(호스트, 예: x86)에서 로봇 제어보드(타겟, 예: ARM)와는 다른 프로세서 구조용 실행 파일을 만들어내는 컴파일 방식 — 성능이 좋은 개발 PC의 자원을 활용하고, 자원이 제한된 타겟 장치에서 직접 컴파일하는 부담을 없앰
- **원격 디버깅**: 개발 PC에서 실행되는 디버거(GDB 등)가 네트워크·시리얼로 타겟 장치에서 실행 중인 별도 프로그램(GDB server 등)과 통신해, 타겟에서 실행 중인 프로그램을 원격으로 중단·값 추적하는 방식 — 타겟 장치에 무거운 디버깅 도구를 직접 설치하지 않아도 됨
- 로봇 소프트웨어 개발에서는 이 둘이 IDE와 통합되어, 개발자가 PC에서 코드를 작성·빌드하고 곧바로 실제 로봇에서 원격으로 디버깅하는 워크플로가 일반적임
- 출처: [Intro to Cross-Compilation - circuitlabs.net](https://circuitlabs.net/intro-to-cross-compilation-why-and-how/), [Remote cross-target debugging with GDB and GDBserver](https://www.linux.com/news/remote-cross-target-debugging-gdb-and-gdbserver/)

### Docker Compose — 여러 컨테이너를 함께 다루는 확장 (신규)
- 기존 페이지2는 Docker 컨테이너 하나의 개념만 다루는데, 로봇 소프트웨어는 흔히 여러 컨테이너(예: 센서 드라이버 컨테이너, 인식 알고리즘 컨테이너, UI 컨테이너)가 함께 동작해야 함
- **Docker Compose**: 여러 컨테이너의 구성(이미지, 네트워크, 볼륨, 실행 순서)을 하나의 설정 파일로 정의해, 명령 하나로 전체 컨테이너 묶음을 함께 시작·중지할 수 있게 하는 도구
- 출처: [Docker Compose Guide - DataCamp](https://www.datacamp.com/tutorial/docker-compose-guide)

## Phase 2 — 자체 검토

- GDB/GDBserver 같은 구체적 도구명은 참고 수준으로만 조사md에 남기고, 페이지 본문에는 "왜 필요한가(개발 PC와 타겟의 프로세서 구조가 다름)"라는 개념 위주로 반영
- Docker Compose는 기존 페이지의 "여러 대의 로봇에 동일 환경 배포" 예시와 자연스럽게 이어지도록, 단일 컨테이너 개념 뒤에 짧게 추가

## Phase 3 — 결론

1개 페이지(2. IDE와 컨테이너 기술)에 신규 개념 2건(크로스컴파일+원격디버깅, Docker Compose) 반영. Box 용어는 `크로스 컴파일과 원격 디버깅(Cross-Compilation·Remote Debugging)` 신규 생성. Docker Compose는 기존 `Docker(컨테이너 기술)` Box 용어에 보강.
