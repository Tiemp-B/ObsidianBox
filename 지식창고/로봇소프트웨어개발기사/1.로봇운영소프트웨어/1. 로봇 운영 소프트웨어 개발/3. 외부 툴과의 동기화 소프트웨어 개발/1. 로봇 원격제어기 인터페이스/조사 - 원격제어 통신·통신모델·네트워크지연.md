# 조사 - 원격제어 통신·통신모델·네트워크지연 (Phase 1~3, 2026-08-07)

이 세세항목("1. 로봇 원격제어기 인터페이스")의 NCS 학습모듈(LM1903080311/312, 학습2 "외부 툴과의 동기화 소프트웨어 개발하기") 필요지식은 **로봇 프로그래밍 방식(교시형/오프라인)만** 다루고, TCP/IP·UDP·MQTT·DDS·WebRTC·통신모델(발행-구독/요청-응답/액션)·HMI·네트워크지연·QoS는 전혀 다루지 않는다 → 이 항목들은 §1-2/1-3에 따라 문제은행 힌트 + 도메인지식(웹조사 검증) 기반으로 구성.

## Phase 1 — 초기 조사

### TCP/IP vs UDP
- TCP: 연결지향, 오류검사·데이터복구·수신확인 제공 → 신뢰성 높음. 연결 수립(3-way handshake)·재정렬·재전송 절차가 지연 유발
- UDP: 비연결형, 전송 전 확인응답/연결수립 없음 → 지연 낮음. 순서·전달 보장 없음
- 로봇 제어 실무: 표준 UDP만으로도 대부분의 로봇 응용에 충분하다는 실측 사례 존재(소비자급 이더넷에서도 1억 패킷 이상 무손실·무순서뒤바뀜 관측, 1600개 센서 1kHz 통신에서도 안정적) — 다만 이는 유선 근거리 네트워크 조건의 사례이며 무선/광역 환경까지 일반화하지 않음
- 실무 아키텍처: 제어 명령 전달은 TCP, 실시간 영상 스트리밍은 UDP로 혼합하는 전통적 조합이 흔함
- 출처: [Analyzing the viability of Ethernet and UDP for robot control](https://ennerf.github.io/2016/11/23/Analyzing-the-viability-of-Ethernet-and-UDP-for-robot-control.html), [TCP vs UDP: Speed, reliability, and application trade-offs](https://eureka.patsnap.com/article/tcp-vs-udp-speed-reliability-and-application-trade-offs)

### DDS(Data Distribution Service)
- OMG(Object Management Group) 표준. 발행-구독 모델 + QoS로 신뢰성 있고 시간 맞는 데이터 전파를 보장. ROS2의 기본 미들웨어
- QoS 정책 중 핵심 2가지:
  - **Reliability**: Best-Effort(확인응답 없이 전송, UDP 패킷 유실 시 구독자가 못 받음) vs Reliable(수신 확인, 필요시 재전송)
  - **History**: KEEP(N)(최근 N개만 보관) vs KEEP ALL(전체 보관, 재전송 대비 완전 복구 가능)
  - (Durability 정책도 존재하나 이번 페이지 범위에서는 생략 — 과도한 세부 실기 영역)
- ROS2 노드 간 통신에는 Durability/Reliability/History 정책이 필요하며 기본값은 각각 volatile/reliable/keep-last
- 출처: [ROS on DDS (design.ros2.org)](https://design.ros2.org/articles/ros_on_dds.html), arXiv 2508.10413 "Probabilistic Latency Analysis of DDS in ROS2"

### WebRTC vs WebSocket
- WebRTC: P2P(브라우저 간 직접 연결, 시그널링 이후), 미디어 경로가 서버를 거치지 않음
- WebSocket: 클라이언트-서버 모델, 모든 통신이 중앙 서버를 거침(관리는 쉽지만 병목 가능)
- WebRTC 지연: 원격 스트리밍에 약 10ms 오버헤드만 추가(나머지는 정적 네트워크 지연). LTE 환경에서 글래스-투-글래스 지연 100~250ms(참고용 수치, RTSP 기본 버퍼링 500~2000ms와 대비) — **이 수치는 조건에 따라 크게 달라지는 예시값**으로, 페이지에는 "WebRTC가 WebSocket보다 지연이 짧다"는 정성적 사실 위주로 반영하고 구체 ms값은 예시 표현으로만 사용
- 로봇 원격제어에서 MQTT(제어 신호)+WebRTC(영상, LiveKit 등 프레임워크 활용)를 조합하는 실제 사례 존재. ROS2로 고해상도 영상을 직접 보내면 500ms 지연·저대역폭이지만 WebRTC 적용 시 30Hz·100ms로 개선된 사례 있음(단일 사례, 일반 법칙으로 단정하지 않음)
- 출처: [Nabto: WebRTC vs WebSocket for IoT](https://www.nabto.com/webrtc-vs-websocket-for-iot/), [WebRTC Latency: A Breakdown](https://transitiverobotics.com/blog/webrtc-latency-breakdown/), arXiv 2510.11421

### ROS2 Topic/Service/Action (공식문서 기준)
- **Topic**: 발행-구독, 지속적 데이터 스트림(센서값, 로봇 상태 등)에 적합
- **Service**: 요청/응답 패턴, 동기적, 1:1 통신, 빠른 요청-응답에 적합
- **Action**: 목표(Goal)-피드백(Feedback)-결과(Result) 패턴. Topic의 비동기성과 Service의 구조를 결합. 장시간 작업(명확한 시작·끝이 있는)에 적합, 진행 중 상태를 계속 확인 가능
- 출처: [ROS2 공식문서 Topics vs Services vs Actions](https://docs.ros.org/en/humble/How-To-Guides/Topics-Services-Actions.html), [design.ros2.org/articles/actions.html](https://design.ros2.org/articles/actions.html)

### 네트워크 QoS — IntServ vs DiffServ (기존 페이지의 정정 필요 지점)
- **IntServ(Integrated Services)**: 통신 시작 전 종단간 대역폭을 미리 예약(RSVP 프로토콜 사용) — 상태유지형이라 대규모 확장에는 복잡·오버헤드 큼
- **DiffServ(Differentiated Services)**: 흐름마다 예약하는 대신 트래픽을 클래스(음성/영상/일반)로 분류해 차등 처리. IP헤더의 DSCP 필드로 패킷을 표시. 확장성이 좋아 기업망에서 더 흔히 쓰임
- 산업 네트워크에서는 IEEE 802.1p(L2 VLAN 태깅), DiffServ/DSCP(L3), 포트/프로토콜 기반 규칙 등을 함께 사용해 제어 트래픽의 지연·지터를 줄임
- **기존 페이지는 "대역폭 예약"과 "우선순위 지정"을 단순 나열했으나, 실제로는 이 둘이 각각 IntServ·DiffServ라는 서로 다른 아키텍처 모델에 해당한다는 점을 재작성 시 명확히 구분**
- 출처: [QoS Explained: DiffServ and IntServ](https://eureka.patsnap.com/article/qos-explained-how-diffserv-and-intserv-prioritize-network-traffic), [QoS in Industrial Networks](https://maplesystems.com/quality-of-service-qos-in-industrial-networks/)

## Phase 2 — 자체 검토·추가조사 필요 항목 식별

- WebRTC 지연 구체 수치(10ms/100~250ms/500~2000ms)는 출처마다 조건이 달라 단일 확정값으로 쓰면 위험 — Phase1에서 이미 "예시값" 처리로 완화함, 추가조사 불필요(정성적 우위만 확정적으로 서술)
- SMTP가 원격제어 부적합한 이유는 이미 기존 페이지에 명확한 논리(설계 목적 자체가 비동기 배치 전달)로 서술돼 있고 별도 표준 문서 근거가 필요한 수치·주장이 아니므로 추가조사 불필요
- DDS Durability 정책은 생략 처리(범위 밖 판단, §1-2 필기 성격에 맞춰 과도한 실기 세부사항 배제)
