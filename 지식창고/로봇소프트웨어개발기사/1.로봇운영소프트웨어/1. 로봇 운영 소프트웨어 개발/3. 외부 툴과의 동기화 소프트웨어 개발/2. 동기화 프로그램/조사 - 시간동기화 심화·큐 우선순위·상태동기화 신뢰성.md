# 조사 - 시간동기화 심화·큐 우선순위·상태동기화 신뢰성 (Phase 1~3, 2026-08-07)

**목표 프레이밍**: 이번 회차부터 조사의 목적은 기존 내용 검증이 아니라 **추가할 정보를 찾는 것**(사용자 확정, 2026-08-07). 기존 4페이지(개요/NTP/생산자-소비자/WebSocket상태동기화)는 이미 정확하므로, 각 페이지에 새로 엮어 넣을 만한 관련 개념·기법을 중심으로 조사했다.

## Phase 1 — 초기 조사

### 시간 동기화 알고리즘 계보 — Cristian's/Berkeley/NTP 비교 (기존 페이지엔 NTP만 있음 → 신규)
- **Cristian's 알고리즘**: 중앙집중형. 단일 시간 서버에 요청해 왕복시간을 측정하고 시각을 보정 — NTP도 이 방식에 기반
- **Berkeley 알고리즘**: 역시 중앙집중형이지만, 정확한 시각원이 없다는 전제. 리더가 여러 팔로워를 폴링해 Cristian's 알고리즘으로 각각의 시각을 얻고, **평균을 계산(이상치 제외)**해 그 보정값을 각 노드에 되돌려줌 — 기준 서버(GPS 등) 없이 노드끼리 합의로 시각을 맞추는 방식
- NTP는 Cristian's 알고리즘에 기반하지만 **시계를 뒤로 되돌리지 않는다는 점**이 다름(두 파일이 같은 타임스탬프를 갖는 등의 부작용 방지), 계층적(Stratum) 프로토콜이라는 점도 차별점
- 출처: [UCSD CSE124 강의자료](https://cseweb.ucsd.edu/classes/sp18/cse124-a/post/schedule/14-Time.pdf), [Berkeley algorithm - Wikipedia](https://en.wikipedia.org/wiki/Berkeley_algorithm)

### PTP(IEEE 1588) — NTP보다 훨씬 정밀한 대안 (기존 페이지에 이름만 있고 원리 없음 → 신규)
- **하드웨어 타임스탬핑**이 핵심 차이: PTP는 메시지가 네트워크 인터페이스 카드(NIC)·스위치를 드나드는 순간을 하드웨어 수준에서 타임스탬프 → 소프트웨어 기반인 NTP(밀리초급)보다 훨씬 정밀(마이크로초 이하)
- 지터의 영향도 하드웨어 타임스탬핑 덕분에 줄어들어, 산업 현장에서 더 안정적
- **로봇 응용**: 자동화 라인의 모션 제어처럼 분산된 I/O·로봇·드라이브가 동기적으로 동작해야 하는 경우, PTP가 로봇·제어 시스템·구성요소의 내부 시계를 동기화해 시스템 전체의 통일된 타임스탬프를 만듦
- 출처: [PTP vs NTP: Industrial Networks](https://www.mikrodev.com/ptp-ieee-1588-vs-ntp-millisecond-precision-time-synchronization-in-industrial-networks-and-scada/), [Time Synchronization in modular collaborative robots (arXiv 1809.07295)](https://arxiv.org/pdf/1809.07295)

### 논리적 시계(Lamport/Vector Clock) — 물리적 시계 동기화의 대안 패러다임 (완전히 새로운 개념 → 신규)
- NTP·PTP는 모두 "물리적 시각 자체"를 맞추는 접근인 반면, **논리적 시계**는 물리적 시각과 무관하게 **이벤트 간 인과관계(순서)**만 일관되게 매기는 접근
- **Lamport 논리적 시계**: 각 프로세스가 이벤트마다 카운터를 증가시키고, 메시지에 발신자의 카운터값을 실어 보냄. "happened-before" 관계(같은 프로세스 내 순서, 메시지 송신→수신)로 인과 순서를 정의. 한계: 두 이벤트가 동시(concurrent)인지, 인과관계가 있는지 구분하지 못하는 **부분 순서**만 제공
- **벡터 시계**: Lamport 시계를 확장해 동시성 여부까지 판별 가능(더 정교하지만 오버헤드 큼)
- **왜 필요한가**: 물리적 시계는 클럭 드리프트·네트워크 지연·처리속도 차이로 완벽히 일치시키기 어려워, 물리적 타임스탬프만으로 전역 이벤트 순서를 신뢰하기 어려움 — 논리적 시계는 물리적 동기화 없이도 인과 순서를 보장
- 출처: [Time, Clocks, and the Ordering of Events in a Distributed System (Lamport 원논문)](https://lamport.azurewebsites.net/pubs/time-clocks.pdf), [Lamport Clock - Baeldung](https://www.baeldung.com/cs/lamport-clock)

### 큐의 우선순위·기아 상태(Starvation) 방지 (기존 생산자-소비자 페이지엔 없음 → 신규)
- 여러 생산자가 서로 다른 중요도의 데이터를 큐에 넣는 경우(예: 비상정지 명령 vs 일반 이동 명령), 단순 FIFO 큐는 긴급한 명령이 먼저 쌓인 일반 명령들 뒤에서 대기해야 하는 문제가 생김 → **우선순위 큐**로 해결
- 우선순위 큐를 그대로 쓰면 반대로 **기아 상태(Starvation)**: 높은 우선순위 메시지가 계속 들어오면 낮은 우선순위 메시지가 무한정 밀릴 위험
- 기아 상태 방지 기법: **에이징(Aging)** — 대기 시간이 길어질수록 그 작업의 우선순위를 점진적으로 높여, 결국은 처리되도록 보장. 또는 우선순위별 소비자 용량을 비례 배분(예: 고우선순위 5개·일반 3개·저우선순위 2개 소비자)하는 방식도 있음
- 출처: [RabbitMQ Priority Queue 문서](https://www.rabbitmq.com/docs/priority), [starvation-free-priority-queue (GitHub)](https://github.com/ori88c/starvation-free-priority-queue)

### WebSocket 상태 동기화의 신뢰성 기법 — 시퀀스 번호·하트비트 (기존 페이지에 없음 → 신규)
- **시퀀스 번호 기반 재동기화**: 서버가 메시지마다 단조증가하는 시퀀스 번호를 부여(클라이언트 타임스탬프가 아니라 서버 측에서 메시지 도착 시 부여). 클라이언트는 마지막으로 받은 시퀀스 번호를 기억해 두었다가, 재연결 시 그 번호를 서버에 알려 **그 이후 놓친 메시지만 재전송**받는 방식 — 서버는 이를 위해 메시지를 일정 기간 버퍼링
- **하트비트(Heartbeat/Ping-Pong)**: 클라이언트가 주기적으로(예: 15~30초) 하트비트를 보내 연결이 "살아있지만 응답 없는" 좀비 연결(zombie connection)을 감지 — 단순히 TCP 연결이 끊겼는지가 아니라, 응용 계층에서 실제로 통신이 되는지를 확인하는 것이 핵심. 하트비트 주기는 통상 가장 짧은 프록시 타임아웃의 약 75% 수준으로 설정
- 이 두 기법은 "완전한 실시간 동기화는 불가능하다"는 기존 페이지의 한계 서술을 실무적으로 어떻게 관리하는지 보여주는 구체적 해법
- 출처: [WebSocket Reconnection: State Sync and Recovery Guide](https://websocket.org/guides/reconnection/), [WebSocket Heartbeat: Ping/Pong, Keep-Alive & Zombie Detection](https://websocket.org/guides/heartbeat/)

- PTP의 구체적 정밀도(마이크로초 이하)는 조건에 따라 다르므로 절대값 대신 "NTP(밀리초)보다 훨씬 정밀"이라는 상대적 서술로 반영
