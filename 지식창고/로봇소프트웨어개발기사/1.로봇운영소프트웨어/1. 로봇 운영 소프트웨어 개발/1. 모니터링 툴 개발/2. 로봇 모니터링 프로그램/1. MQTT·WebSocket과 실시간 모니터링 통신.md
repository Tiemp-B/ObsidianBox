# Summary

로봇 모니터링 프로그램은 제어기에서 생성된 상태 데이터를 **수집 → 통신 → 저장/처리 → 시각화**의 흐름으로 전달하는 응용 계층 소프트웨어다. 이 중 통신 계층에서 가장 널리 쓰이는 두 프로토콜이 **[[MQTT]]** 와 **[[WebSocket]]** 이다. MQTT는 다수의 저전력·저대역폭 센서/로봇 노드가 브로커를 통해 비동기로 데이터를 발행(publish)하는 구조에 적합하고, WebSocket은 브라우저 기반 대시보드처럼 클라이언트-서버 간 저지연 양방향 실시간 통신이 필요한 구간에 적합하다. 두 프로토콜은 경쟁 관계가 아니라 **역할이 다른 상호 보완적 구성요소**로 이해해야 한다.

# Notes

<aside>모니터링 프로그램의 통신 계층</aside>

로봇 모니터링 프로그램은 대체로 아래와 같은 데이터 흐름을 가지며, 이 페이지는 그중 **통신 계층**을 다룬다.

1. **수집**: 제어기/센서로부터 상태 데이터 획득
2. **통신**: 수집된 데이터를 네트워크로 전달 ← MQTT, WebSocket이 위치하는 계층
3. **저장/처리**: 로깅, 이상치 탐지, 스트림 처리 ([[5. 데이터 로깅과 이상치 탐지]], [[6. 스트림 처리(Stream Processing)와 실시간 데이터 파이프라인]] 참고)
4. **시각화**: 대시보드, 알람 ([[4. 데이터 시각화와 알람(HMI)]] 참고)

통신 계층의 방식은 크게 **발행-구독(Publish-Subscribe)** 방식과 **요청-응답(Request-Response)** 방식으로 나뉘며, MQTT는 전자, 일반 HTTP는 후자에 해당한다. WebSocket은 요청-응답 방식(HTTP)에서 출발했지만 연결 수립 이후에는 양방향 스트림처럼 동작한다는 점에서 둘의 경계에 걸쳐 있다.

<aside>MQTT 개요</aside>

**[[MQTT]]** (Message Queuing Telemetry Transport)는 [[발행-구독 모델(Publish-Subscribe)|발행-구독(Pub/Sub)]] 구조의 경량 메시징 프로토콜이다.

- **브로커(Broker)**: 발행자(Publisher)와 구독자(Subscriber)를 중개하는 서버. 발행자와 구독자는 서로를 직접 알 필요가 없다(느슨한 결합)
- **토픽(Topic)**: 메시지를 분류하는 문자열 경로(예: `robot/1/joint_states`). 구독자는 특정 토픽을 구독(subscribe)해야 해당 메시지를 수신한다
- TCP 기반이며 헤더 오버헤드가 작아 **저대역폭·배터리 제약이 있는 다수의 센서/로봇 노드**가 원격지 서버로 텔레메트리를 보내는 용도에 적합하다

<aside>MQTT QoS 레벨</aside>

MQTT는 메시지 전달 신뢰도를 3단계 **QoS(Quality of Service)** 로 선택할 수 있다.

| QoS 레벨 | 이름 | 동작 |
|---|---|---|
| QoS 0 | At most once | 메시지를 **한 번만 전송**하고 수신 확인(ACK)을 하지 않는다. 유실 가능성이 있지만 오버헤드가 가장 작다 |
| QoS 1 | At least once | 수신 확인이 올 때까지 재전송한다. 유실은 없지만 **중복 수신**이 발생할 수 있다 |
| QoS 2 | Exactly once | 4단계 핸드셰이크로 **정확히 한 번**만 전달되도록 보장한다. 신뢰도는 가장 높지만 오버헤드도 가장 크다 |

"한 번만 시도하고 수신 여부를 확인하지 않는" 레벨은 **QoS 0**이다. 신뢰도가 높을수록 지연·오버헤드가 커지는 트레이드오프 관계이므로, 모니터링 데이터의 성격(예: 주기적으로 갱신되어 유실돼도 다음 값으로 대체 가능한 센서 값 vs 반드시 전달되어야 하는 알람/명령)에 따라 QoS를 다르게 선택하는 것이 실무적으로 중요하다.

<aside>WebSocket 개요</aside>

**[[WebSocket]]** 은 하나의 TCP 연결 위에서 클라이언트-서버 간 **양방향(Full-Duplex) 실시간 통신**을 제공하는 프로토콜이다.

- 연결은 HTTP 핸드셰이크(Upgrade 요청)로 시작하지만, 이후에는 HTTP와 독립적인 자체 프레임 방식으로 동작한다
- 한 번 연결을 수립하면 **지속적으로 열려 있는 연결(Persistent Connection)** 을 유지하며, 이후 메시지 교환마다 매번 새로 연결을 맺거나 요청 헤더 전체를 반복 전송할 필요가 없다
- 서버가 클라이언트의 요청 없이도 먼저 데이터를 보낼 수 있다(Server Push) — 이는 매 메시지마다 클라이언트가 먼저 요청해야 하는 일반 HTTP 요청-응답 모델과의 핵심 차이다

<aside>WebSocket과 HTTP 폴링 비교</aside>

로봇 모니터링 대시보드에서 실시간 값을 갱신하는 방법은 WebSocket 외에도 HTTP 폴링(Polling) 방식이 있다.

| 항목 | HTTP 폴링 | WebSocket |
|---|---|---|
| 연결 방식 | 매 요청마다 새로 연결 | 최초 1회 연결 후 유지 |
| 오버헤드 | 요청마다 HTTP 헤더 반복 전송 | 연결 후에는 프레임 오버헤드만 소요 |
| 지연 | 폴링 주기에 종속 | 이벤트 발생 즉시 전달 가능 |
| 서버→클라이언트 푸시 | 불가(클라이언트가 먼저 요청해야 함) | 가능 |

<aside>MQTT vs WebSocket 선택 기준</aside>

**예시 — 로봇 플릿(fleet) 모니터링 시스템 구성**: 수십 대의 이동로봇이 배터리·위치·에러 코드를 5초 주기로 클라우드에 보고할 때는 오버헤드가 작은 **MQTT**로 각 로봇이 브로커에 토픽별로 발행하고, 관제 센터의 **웹 대시보드**는 서버가 MQTT 브로커를 구독한 뒤 그 데이터를 다시 **WebSocket**으로 브라우저에 실시간 중계하는 조합이 실무에서 흔히 쓰인다. 즉 로봇↔서버 구간은 MQTT, 서버↔브라우저 구간은 WebSocket으로 역할을 분담하는 것이 전형적인 패턴이다.

<aside>핵심 정리</aside>

- MQTT는 [[발행-구독 모델(Publish-Subscribe)|발행-구독]] 기반의 경량 프로토콜이며, 브로커가 발행자와 구독자를 중개한다
- MQTT QoS: **0(최대 한 번, 미확인) / 1(최소 한 번, 중복 가능) / 2(정확히 한 번)** — 신뢰도와 오버헤드는 트레이드오프
- WebSocket은 **단일 연결 위의 양방향 실시간 통신**이며, 서버 푸시가 가능하고 매 메시지마다 재연결이 필요 없다 — 이 반대로 서술하는 선택지가 오답 함정
- 실무에서는 로봇↔서버는 MQTT, 서버↔대시보드는 WebSocket으로 역할을 분담하는 구성이 일반적
