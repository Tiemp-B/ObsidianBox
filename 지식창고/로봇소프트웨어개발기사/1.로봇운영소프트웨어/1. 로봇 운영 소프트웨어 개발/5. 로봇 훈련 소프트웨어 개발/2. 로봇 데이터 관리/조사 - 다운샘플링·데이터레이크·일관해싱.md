# 조사 - 다운샘플링·데이터레이크·일관해싱 (2026-08-07)

NCS 대응 모듈은 별도 확인 없음(§1-2에 따라 문제은행+도메인지식 기반, 데이터베이스 일반 지식 영역). 기존 4페이지가 이미 정확한 도메인지식으로 작성돼 있고, 개요(허브) 링크도 정상. 문제은행 6문항 전부 기존 페이지에서 커버 확인. 목표(추가정보 발굴)에 맞춰 각 페이지에 새로 엮을 개념을 조사했다.

## Phase 1 — 조사

### 다운샘플링(Downsampling)·롤업 — 시계열 DB의 보존 정책 심화 (신규)
- 기존 페이지2는 "오래된 데이터는 요약해 압축하거나 자동 삭제하는 보존 정책을 쓴다"고만 서술하고, "요약"이 구체적으로 무엇인지는 다루지 않았음
- **다운샘플링(Downsampling)**: 세밀한 원본 데이터(예: 1초 단위)를 시간 구간별로 평균·최댓값 등 집계 함수를 적용해 더 성긴 간격(예: 1시간 단위)의 요약 데이터로 만드는 것 — 이렇게 만든 요약 데이터를 **롤업(Rollup)** 이라 부름
- 최근 데이터는 원본 그대로 정밀하게 보관하고, 오래된 데이터는 다운샘플링한 롤업만 남겨 저장 공간을 줄이면서도 장기 추세 분석은 계속 가능하게 하는 것이 일반적인 전략(예: InfluxDB의 Continuous Query, TimescaleDB의 Continuous Aggregate)
- 출처: [Downsampling and Data Retention - InfluxData](https://docs.influxdata.com/influxdb/v1/guides/downsample_and_retain/), [How to manage long-term data storage with downsampling - TigerData](https://www.tigerdata.com/blog/how-to-proactively-manage-long-term-data-storage-with-downsampling)

### 데이터 레이크(Data Lake) — 데이터 웨어하우스와의 대비 (신규)
- 기존 페이지3은 데이터 웨어하우스만 다루는데, 흔히 함께 비교되는 **데이터 레이크**가 빠져 있었음
- **데이터 웨어하우스**: 스키마를 미리 정하고(Schema-on-Write) 정제된 구조적 데이터만 저장 — ETL을 거친 뒤 적재
- **데이터 레이크**: 정형·비정형을 가리지 않고 **원본 그대로(raw)** 저장해 두고, 나중에 조회할 때 필요한 구조를 적용(Schema-on-Read) — 로봇의 원본 센서 로그, 이미지 등을 가공 전에 우선 통째로 보관하는 용도에 적합
- 두 방식을 절충한 것이 최근의 **데이터 레이크하우스(Lakehouse)** 개념(참고 수준)
- 출처: [Data Lakes vs Data Warehouses - Databricks](https://www.databricks.com/blog/data-lakes-vs-data-warehouses-what-your-organization-needs-know), [Schema-on-Read vs Schema-on-Write - Dremio](https://www.dremio.com/wiki/schema-on-read-vs-schema-on-write/)

### 일관 해싱(Consistent Hashing) — 샤딩의 핫스팟 문제 해결책 (신규)
- 기존 페이지4는 "샤딩 키를 잘못 고르면 핫스팟이 생긴다"는 문제만 지적하고, 이를 완화하는 구체적 기법은 다루지 않았음
- 단순히 `해시값 % 샤드수`로 나누면, 샤드 수가 바뀔 때(서버 추가/제거) 거의 모든 데이터의 배치가 재계산돼야 하는 문제가 있음
- **일관 해싱(Consistent Hashing)**: 해시 값의 범위를 원형(ring) 구조로 배치해 각 샤드가 일부 구간을 담당하게 하는 방식 — 샤드가 추가·제거되어도 **그 인접 구간의 데이터만 재배치**되면 되므로, 전체 데이터를 다시 섞는 것보다 데이터 이동량이 훨씬 적고, 균등 분산으로 핫스팟도 줄어듦
- 리샤딩(기존 페이지에 이미 있는 개념) 시 데이터 이동을 최소화하는 실제 구현 기법으로 자연스럽게 연결됨
- 출처: [How Consistent Hashing is Better in Handling Hotspots - GeeksforGeeks](https://www.geeksforgeeks.org/how-consistent-hashing-is-better-in-handing-hotspots-than-simple-hashing/), [4 Data Sharding Strategies - Yugabyte](https://www.yugabyte.com/blog/four-data-sharding-strategies-we-analyzed-in-building-a-distributed-sql-database/)

## Phase 2 — 자체 검토

- 다운샘플링은 특정 제품(InfluxDB/TimescaleDB) 기능명(Continuous Query 등)은 조사md에만 참고로 남기고, 페이지 본문에는 제품 종속 없이 "다운샘플링/롤업"이라는 개념만 반영
- 데이터 레이크하우스(Lakehouse)는 최신 절충 개념이라 조사md에만 참고 수준으로 남기고 페이지 본문에는 반영하지 않음(핵심은 데이터 웨어하우스 vs 데이터 레이크의 스키마 시점 대비)
- 일관 해싱은 수식·해시링 세부 알고리즘은 넣지 않고 "왜 필요한가(리샤딩 시 이동량 최소화)"라는 개념만 반영

## Phase 3 — 결론

3개 페이지(2. 시계열DB/NoSQL, 3. 데이터웨어하우스/ETL, 4. 데이터마이닝/샤딩)에 각각 1개씩 신규 개념 반영. Box 용어는 일관 해싱(Consistent Hashing), 데이터 레이크(Data Lake) 신규 생성.
