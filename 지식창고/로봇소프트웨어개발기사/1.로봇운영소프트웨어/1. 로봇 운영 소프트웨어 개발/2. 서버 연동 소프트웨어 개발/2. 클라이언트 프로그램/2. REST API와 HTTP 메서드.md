# Summary

**[[REST API(Representational State Transfer)|REST API]]**는 URI로 자원(Resource)을 표현하고, HTTP 메서드로 그 자원에 대한 행위를 표현하는 방식이다. GET·POST·PUT·PATCH·DELETE는 각각 조회·생성·전체 교체·부분 수정·삭제에 대응하며, 특히 **PUT과 PATCH는 둘 다 "수정"이라는 점에서 혼동되지만 교체 범위가 다르다** — PUT은 자원 전체를 교체하고, PATCH는 일부 필드만 수정한다.

# Notes

<aside>REST와 자원(Resource) 개념</aside>

**REST(Representational State Transfer)**는 서버의 자원을 URI로 식별하고, 그 자원에 대한 조작을 HTTP 메서드로 표현하는 아키텍처 스타일이다. 예를 들어 `/robots/1`이라는 URI는 "1번 로봇"이라는 자원을 가리키고, 이 URI에 어떤 HTTP 메서드를 사용하느냐에 따라 조회·수정·삭제 등의 의미가 달라진다.

<aside>HTTP 메서드 개념</aside>

| 메서드 | 의미 |
|---|---|
| GET | 자원 조회 |
| POST | 새 자원 생성 |
| PUT | 자원 전체 교체 |
| PATCH | 자원 일부 수정 |
| DELETE | 자원 삭제 |

<aside>PUT과 PATCH의 차이</aside>

- **PUT**: 요청 본문에 자원의 **모든 필드**를 담아 보내며, 서버는 기존 자원을 그 내용으로 통째로 교체한다 — 요청에 포함되지 않은 필드는 기본값이나 null로 덮어써질 수 있다
- **PATCH**: 요청 본문에 **변경할 필드만** 담아 보내며, 서버는 나머지 필드는 그대로 둔 채 지정된 필드만 수정한다

"PUT과 PATCH의 차이"를 묻는 문제의 정답은 바로 이 **전체 교체(PUT) vs 부분 수정(PATCH)**의 구분이다.

<aside>멱등성(Idempotency)</aside>

**[[멱등성(Idempotency)|멱등성]]**은 같은 요청을 여러 번 반복해도 서버의 최종 상태가 달라지지 않는 성질이다.

| 메서드 | 멱등성 |
|---|---|
| GET | 멱등(조회만 하므로 여러 번 호출해도 상태 변화 없음) |
| PUT | 멱등(같은 내용으로 여러 번 교체해도 결과는 동일) |
| DELETE | 멱등(이미 삭제된 자원을 다시 삭제 요청해도 최종 상태는 "삭제됨"으로 동일) |
| POST | 비멱등(호출할 때마다 새 자원이 생성됨) |
| PATCH | 구현에 따라 다름 — "필드에 값을 1 증가시켜라" 같은 PATCH는 호출할 때마다 결과가 달라지므로 비멱등으로 취급되는 경우가 많음 |

<aside>예시 — 로봇 제어 명령에서의 HTTP 메서드 적용</aside>

**예시**: 로봇 관제 API를 설계할 때, 로봇 목록 조회는 `GET /robots`, 새 작업(Job) 등록은 `POST /robots/1/jobs`, 로봇 설정값 전체를 새 값으로 교체할 때는 `PUT /robots/1/config`, 배터리 경고 임계값 하나만 수정할 때는 `PATCH /robots/1/config`, 작업 취소는 `DELETE /robots/1/jobs/5`로 설계하는 것이 자연스럽다.

---

<aside>핵심 정리</aside>

- REST API는 URI로 자원을, HTTP 메서드로 행위를 표현한다
- **PUT은 자원 전체 교체, PATCH는 일부 필드만 부분 수정** — 이것이 PUT과 PATCH의 핵심 차이
- 멱등성은 같은 요청을 반복해도 결과가 같은 성질이며, GET·PUT·DELETE는 멱등, POST는 비멱등, PATCH는 구현에 따라 다르다
