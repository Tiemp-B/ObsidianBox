# Summary

**서버 프로그램**은 [[클라이언트-서버 모델(Client-Server Model)|클라이언트-서버 구조]]에서 클라이언트의 요청을 받아 처리하고, 자원(데이터·연산·상태)을 중앙에서 관리·중개하는 프로그램이다. 로봇 관제 시스템에서는 다수의 로봇과 다수의 클라이언트(대시보드, 모바일 앱 등) 사이에서 상태를 취합하고 명령을 중계하는 중심 노드 역할을 한다. 화면 렌더링이나 사용자 입력 처리처럼 사용자와 직접 맞닿는 부분은 서버가 아니라 [[2. 클라이언트 프로그램|클라이언트]]의 역할이라는 점이 서버의 역할을 구분하는 핵심 기준이다.

# Notes

<aside>클라이언트-서버 모델 개념</aside>

**[[클라이언트-서버 모델(Client-Server Model)|클라이언트-서버 모델]]**은 서비스를 요청하는 쪽(클라이언트)과 서비스를 제공하는 쪽(서버)의 역할을 분리한 구조다. 클라이언트가 요청(Request)을 보내면 서버가 이를 처리해 응답(Response)을 돌려주는 **요청-응답(Request-Response)** 방식이 기본 통신 패턴이다.

<aside>서버의 특성</aside>

| 특성 | 설명 |
|---|---|
| 상시 대기(Listening) | 클라이언트의 요청이 언제 들어올지 모르므로 지정된 포트에서 연결을 항상 대기 |
| 다중 클라이언트 동시 처리 | 하나의 서버가 여러 클라이언트의 요청을 동시에(또는 짧은 시간에 번갈아) 처리 ([[2. 동시성 처리 모델]] 참고) |
| 자원의 중앙 집중 관리 | 데이터·연산 자원을 서버 쪽에 모아두고 여러 클라이언트가 공유하도록 중개 |

다중 클라이언트 동시 처리는 서버의 핵심 특성이며, 서버의 요건은 사양의 절대적 우위가 아니라 **상시 가용성과 동시 처리 능력**에 있다.

<aside>서버 프로그램의 주요 역할</aside>

| 역할 | 설명 |
|---|---|
| 요청 처리(Request Handling) | 클라이언트의 요청을 해석하고 그에 맞는 처리 로직 실행 |
| 데이터/자원 관리 | 데이터베이스, 파일 등 공유 자원에 대한 접근을 중개 ([[4. DB 연동과 트랜잭션]] 참고) |
| 인증·세션 관리 | 클라이언트(사용자)의 로그인 상태·권한을 관리 ([[3. 세션과 상태 관리]] 참고) |
| 상태 취합·중계 | 다수 로봇의 상태 데이터를 취합해 클라이언트에 제공하거나, 클라이언트의 명령을 로봇에 중계 |

반대로 **화면 렌더링, 사용자 입력 이벤트 처리**처럼 사용자와 직접 상호작용하는 부분은 서버가 아니라 클라이언트 프로그램의 역할이다. "서버가 클라이언트의 화면 UI를 직접 그린다"는 서술은 서버-클라이언트의 역할 분담을 혼동한 오답 함정으로 자주 출제된다.

<aside>로봇 제어 시스템에서 서버 역할의 경계</aside>

로봇 제어 시스템에 서버-클라이언트 구조를 적용할 때도, **서버가 로봇의 실시간 폐루프 제어(서보 위치 제어, 전류 루프 등)를 직접 수행하는 것은 아니다.** 그런 고속·결정론적 제어는 로봇 자체의 제어기(컨트롤러)가 담당하고, 서버는 그보다 상위에서 명령을 하달하거나 상태를 취합하는 역할에 머무른다 — [[2. SCADA 구조와 산업용 모니터링 시스템]]에서 다룬 "SCADA는 고속 폐루프 제어를 직접 하지 않는다"는 구도와 동일하다. "서버가 로봇의 서보 제어 루프를 직접 담당한다"는 서술은 서버와 로봇 제어기의 역할을 혼동한 오답 함정이다.

<aside>서버 프로그램의 유형</aside>

| 유형 | 역할 |
|---|---|
| 웹 서버(Web Server) | HTTP 요청을 받아 정적/동적 컨텐츠 제공 |
| 애플리케이션 서버(Application Server) | 비즈니스 로직(명령 검증, 권한 판단 등) 수행 |
| 데이터베이스 서버(DB Server) | 데이터 저장·조회·갱신 처리 |

로봇 관제 시스템에서는 이 세 유형이 하나의 프로세스에 통합되어 있을 수도, 서비스 규모에 따라 물리적으로 분리되어 있을 수도 있다.

<aside>무상태 서버와 상태유지 서버</aside>

- **무상태(Stateless) 서버**: 각 요청을 이전 요청과 무관하게 독립적으로 처리 — 서버가 클라이언트별 상태를 기억하지 않는다
- **상태유지(Stateful) 서버**: 클라이언트별 상태(로그인 세션 등)를 서버가 기억하고 이후 요청에서 참조

이 구분은 뒤에서 다룰 [[3. 세션과 상태 관리|세션 관리]]와 [[5. 로드밸런싱과 확장성|로드밸런싱/확장성]]에서 왜 "상태를 어디에 둘 것인가"가 중요한 설계 결정인지를 이해하는 기반이 된다.

<aside>예시 — 로봇 플릿 관제 서버</aside>

**예시**: 수십 대의 로봇을 운용하는 관제 서버는 각 로봇으로부터 상태 데이터를 수신해 취합하고(자원 관리), 운영자의 웹 대시보드 요청에 그 취합된 상태를 응답하며(요청 처리), 운영자가 대시보드에서 내린 정지/재시작 명령을 해당 로봇에 중계한다(상태 취합·중계). 이때 대시보드 화면에 그래프를 그리는 것은 서버가 아니라 클라이언트(브라우저)의 몫이다.

<aside>핵심 정리</aside>

- 서버는 **상시 대기·다중 클라이언트 동시 처리·자원 중앙 관리**가 핵심 특성이며, 사양이 클라이언트보다 항상 높아야 하는 것은 아니다
- 서버의 역할은 요청 처리·데이터 관리·인증/세션 관리·상태 중계이며, **화면 렌더링·사용자 입력 처리는 클라이언트의 역할**
- 로봇 제어 시스템에서도 **서버는 로봇의 실시간 폐루프 제어를 직접 수행하지 않는다** — 이는 로봇 제어기 자체의 몫이며, SCADA와 동일한 감시/상위 명령 구도
- 웹 서버·애플리케이션 서버·DB 서버로 유형을 나눌 수 있고, 하나의 프로세스에 통합되거나 분리될 수 있음
- 무상태/상태유지 구분은 이후 세션 관리·로드밸런싱 설계와 직결됨
