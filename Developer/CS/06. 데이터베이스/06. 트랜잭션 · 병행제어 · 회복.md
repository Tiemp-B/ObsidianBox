# Notes

<aside>트랜잭션과 ACID</aside>

트랜잭션(Transaction)은 데이터베이스의 논리적 작업 단위이며, 다음 네 가지 특성을 만족해야 한다.

- **원자성(Atomicity)**: 전부 반영되거나 전혀 반영되지 않음 (All or Nothing)
- **일관성(Consistency)**: 실행 전후로 데이터의 일관성이 유지됨
- **격리성(Isolation)**: 실행 중인 트랜잭션은 다른 트랜잭션의 간섭을 받지 않음
- **지속성(Durability)**: 완료된 트랜잭션의 결과는 영구히 반영됨

---

<aside>병행 수행의 문제점</aside>

여러 트랜잭션을 동시에 실행할 때 제어가 없으면 다음 문제가 생긴다.

- **갱신 손실(Lost Update)**: 한 트랜잭션의 갱신을 다른 트랜잭션이 덮어씀
- **현황 파악 오류(Dirty Read)**: 완료되지 않은 중간 값을 읽음
- **모순성(Inconsistency)**: 데이터가 서로 일치하지 않게 됨
- **연쇄 복귀(Cascading Rollback)**: 한 트랜잭션의 롤백이 관련 트랜잭션의 롤백을 유발

---

<aside>병행제어 기법 - 로킹</aside>

데이터에 잠금(Lock)을 걸어 상호 배제로 접근을 제어한다.

- **공유 락(S-Lock)**: 읽기 전용, 여러 트랜잭션이 동시 공유 가능
- **배타 락(X-Lock)**: 읽기·쓰기 독점, 다른 락 불가
- **로킹 단위(Granularity)**: 크면(DB·테이블) 제어는 쉽지만 병행성↓, 작으면(레코드·필드) 병행성↑·오버헤드↑
- **2단계 로킹(2PL)**: 확장 단계(락 획득만) → 축소 단계(락 해제만). 직렬 가능성을 보장하나 교착상태(Deadlock) 발생 가능

---

<aside>병행제어 기법 - 타임스탬프 순서</aside>

트랜잭션에 고유한 시간 스탬프를 부여하고 그 순서대로 직렬화한다.

- 실행 순서를 미리 정하므로 **교착상태가 발생하지 않음**
- 충돌 시 롤백하며, 이로 인한 연쇄 복귀가 생길 수 있음

---

<aside>병행제어 기법 - 낙관적 검증</aside>

충돌이 드물다고 낙관적으로 가정하고, 트랜잭션 수행 중에는 검사 없이 진행한다.

- 커밋 직전 **검증(Validation) 단계**에서 충돌 여부를 확인해 문제가 있으면 롤백
- 판독(Read) → 확인(Validation) → 기록(Write)의 3단계로 동작

---

<aside>병행제어 기법 - 다중 버전(MVCC)</aside>

데이터를 갱신할 때 덮어쓰지 않고 여러 버전을 유지한다.

- 읽기 작업은 적절한 이전 버전을 참조하여 **읽기·쓰기가 서로 차단되지 않음**
- PostgreSQL, Oracle 등 실제 DBMS에서 채택

---

<aside>트랜잭션 격리 수준</aside>

격리 수준이 낮을수록 병행성은 높고 일관성은 낮으며, 높을수록 그 반대이다.

- **READ UNCOMMITTED**: 커밋 안 된 데이터도 읽음 → Dirty Read 발생
- **READ COMMITTED**: 커밋된 데이터만 읽음 → Dirty Read 방지 (다수 DBMS 기본값)
- **REPEATABLE READ**: 트랜잭션 내 같은 조회는 항상 동일 결과 → Non-Repeatable Read 방지
- **SERIALIZABLE**: 완전 직렬 실행처럼 격리 → Phantom Read까지 방지, 병행성 최저

세 가지 이상현상: Dirty Read(미완료 값 읽기), Non-Repeatable Read(반복 조회 시 값 변경), Phantom Read(반복 조회 시 없던 행 출현)

---

<aside>회복 기법 - REDO와 UNDO</aside>

장애 발생 시 데이터베이스를 일관된 상태로 되돌리는 것이 회복(Recovery)이며, 로그(Log)를 기반으로 수행한다.

- **REDO(재실행)**: 이미 완료(commit)된 트랜잭션의 변경을 로그의 after image로 다시 반영
- **UNDO(취소)**: 완료되지 못한 트랜잭션의 변경을 로그의 before image로 되돌림

---

<aside>회복 기법의 종류</aside>

- **즉시 갱신(Immediate Update)**: 변경을 즉시 DB에 반영. 회복 시 UNDO와 REDO가 모두 필요
- **지연 갱신(Deferred Update)**: 커밋 전까지 변경을 로그에만 기록. 회복 시 REDO만 필요(UNDO 불필요)
- **검사점(Checkpoint) 회복**: 주기적으로 검사점을 기록해, 장애 시 검사점 이후만 회복하여 시간을 단축
- **그림자 페이징(Shadow Paging)**: 원본 페이지 테이블(그림자)을 보존하고 변경은 사본에 수행, 장애 시 그림자로 복원
